## Approved decisions

These decisions were approved before implementation. They override the generic M9 text in
`MASTER_PLAN.md`.

- **Labels (D1–D3).** Labels are `relevant` / `borderline` / `not_relevant`, with a separate
  `relation` facet.
  - NDCG gains are 2 / 1 / 0. Strict binary relevance is primary and lenient is secondary.
  - A complement is `not_relevant` with relation `complement`.
- **Blind annotation (D4).** Sources, ranks, scores and parser output are hidden while
  labelling.
- **Single annotator (D5).** Exactly one human annotator, `ann-1`.
  - The primary round is sealed first.
  - A 72-hour-delayed intra-annotator consistency check re-labels `ceil(20% × N)` items.
  - No inter-annotator agreement is claimed. Required disclosure: *"The Golden Dataset was
    reviewed by one human annotator; no independent inter-annotator agreement is claimed."*
  - AI is never an annotator.
  - *Amended 2026-10-15 by `review-2`* (the text above is kept as the historical review-1
    decision): the delayed intra-annotator round is replaced by a blind second-human
    review of the same cs-1 sample, reported as inter-annotator agreement. See "Review
    protocol amendment `review-2`".
- **Pilot vs test (D6, D13).** The 20-query pilot is development / rubric-calibration data and
  is never final test evidence.
  - The held-out test partition is authored separately later and sealed.
  - It will have a separately reported Hinglish slice, provisionally at least 20%.
  - No pilot query and no `seen_in_development` query may enter it.
- **Gold constraints beyond fp-1 (D7).** Gold constraints may name fields fp-1 cannot filter.
  `fp1_filterable` is validated per field, never chosen freely.
- **Hidden attributes (D8).** Availability, rating, review count and seller are hidden during
  annotation.
- **Pool policy `pool-1` (D9), implemented in C2.** Depth 20, eligibility completion of at most
  25, 4 deterministic negatives, and a hard cap of 60 per query.
  - Over the cap: annotation export is refused and the pool is never trimmed.
- **Provenance (D12).** Only its checksum is committed until labels freeze.
- **Session C1 decisions (2026-10-05):**
  1. The pilot table is AI-drafted and confirmed by `ann-1`. The authoring attestation records
     this (below).
  2. Semantic intent, price preference and exact series/model intent are typed soft signals.
  3. In `women running shoes`, gender=women is a strict hard constraint. Unisex does not satisfy
     it; the rubric may still allow `borderline`/`substitute`.
  4. No contradictory-constraint query is added. The gap is disclosed below.
  5. `rubric-1` is declared at `queries_frozen`. A rubric change after freezing creates a new
     golden version; version 1 is never mutated.
  6. Eligibility completion (C2) is all-or-nothing:
     - it runs only for queries with at least one hard constraint and at most 25 products
       satisfying all of them;
     - it then adds every missing satisfied product;
     - a larger eligible set is never truncated.
  7. `seen_in_development` is true for the five texts with repository evidence (below).

## Gold constraints and soft signals

Records in `evals/contracts/models.py`:

- **`GoldConstraint`** has a field, an operator (`eq`, or `lte`/`gte` for price), a typed value,
  a hardness, `fp1_filterable`, `annotator_handle` and `recorded_at`.
  - Hard fields: category, brand, ram_gb, storage_gb, storage_type, storage_interface, price,
    processor, subcategory, gender, anc, wireless, connectivity.
- **Soft-only fields** are refused as hard and are never fp-1-filterable. Their vocabularies are
  qu-1's closed sets:
  - `semantic_intent`: gaming, coding, student, lightweight, premium, comfort, travel, office;
  - `price_preference`: low.
- **`ProductIntent`** is an exact series/model intent (kinds `series`, `model_code`). Its value
  must be a token of some catalog title. It never feeds eligibility.

### Filter support vs. qu-1 extraction

These are two separate facts:

1. `fp1_filterable` (on `GoldConstraint`, per field): fp-1 *could* enforce the field once
   supplied.
2. `QueryExtraction` (generated, `query_extraction.jsonl`): what qu-1 *actually extracted* from
   this exact query, and whether fp-1 actually applied a filter.
   - `status` is one of `extracted`, `extracted_other_value`, `not_extracted` or
     `no_parser_field`.
   - It also records `parsed_value` and `fp1_applied`.

Extraction gaps visible in the pilot (from the deterministic code; regenerated by `verify`):

- **gq-p06:** price is fp-1-filterable, but qu-1 does not parse `under 15000` → `not_extracted`,
  not applied.
- **gq-p16:** brand (`samsng`) and storage (`128gb`, a bare-capacity ambiguity) →
  `not_extracted`.
- **gq-p17:** category (`headfones`) → `not_extracted`.
- **`no_parser_field`:** processor (p04), subcategory and gender (p12), anc (p17) and the Lumen
  series intent. They are never presented as parser output.
- **Soft signals qu-1 does extract:** `gaming` (p11, p13), `office` (p15), `sasta` → low (p14).

Only qu-1's values for gold items are recorded. Extra parser output with no gold counterpart is
not recorded in C1.

## Eligibility (`evals/contracts/eligibility.py`)

A pure, deterministic catalog fact. It is **not relevance** and creates no label.

- **Only hard gold constraints take part**, whether or not they are fp-1-filterable. Soft
  signals and series intents never do.
- **Status per constraint:**
  - `satisfied` / `violated`;
  - `unknown`: the attribute exists for the category but the value is missing;
  - `not_applicable`: the attribute cannot exist for the product, e.g. RAM on shoes, or a shoe
    subcategory on a laptop. It counts as a violation overall.
- **Matching is literal:**
  - exact brand, category, processor and integer capacities;
  - storage medium and interface are compared separately;
  - price bounds are inclusive.
- **Separate overalls.** `hard_overall` and `fp1_overall` (fp-1 fields only) are computed
  separately.
- **Separate counts.** `summarize` reports unknown and not-applicable evaluations separately.
  In the committed seed, none of the pilot's hard constraints has an unknown value.

### Human confirmation

The freeze command is `ann-1`'s own statement of review. An AI assistant must never run it.

```text
uv run python -m evals.runners.freeze_queries preview
uv run python -m evals.runners.freeze_queries freeze --annotator ann-1 \
    --confirm-human-review --input-sha256 <sha256 printed by preview>
```

`--input-sha256` binds the confirmation to the exact input bytes reviewed. A changed input is
refused.

## Session C2: candidate pool, annotation tooling and evaluator

### Pool policy `pool-1` as implemented

`evals/contracts/pooling.py` (pure) builds each query's pool in this order. The result is
independent of input order, uses no random sampling, and creates no label.

1. **Source union.** Six sources, each called once per query at `top_k = 20`
   (`POOL_SOURCE_TOP_K = POOL_DEPTH`). Results are deduplicated by product id.

   | System | Endpoint | Score recorded (private) |
   |---|---|---|
   | `v0_lexical` | `/search` | `lexical_score` |
   | `dense_only` | `/search/dense` | `dense_score` |
   | `v1_hybrid` | `/search/hybrid` | `rrf_score` |
   | `v2_filtered` | `/search/filtered` | `rrf_score` |
   | `v3_reranked_d10` | `/search/reranked`, reranker depth 10 | `rerank_score` (null beyond the depth) |
   | `v3_reranked_d20` | `/search/reranked`, reranker depth 20 | `rerank_score` |

2. **Eligibility completion** (all-or-nothing, C1 decision 6). It runs only for a query with at
   least one hard constraint and 1–25 hard-eligible products, and adds every eligible product
   not already pooled.
   - It never runs for zero eligible, more than 25 eligible, or no hard constraint.
   - It never uses semantic intent, price preference or series intent.
3. **Deterministic negatives.** Four per query, chosen from products not yet pooled, in
   `sha256("pool-1|query_id|product_id")` order:
   - two **same-category**: in the hard gold category, violating another hard constraint;
   - two **other-category**: outside it, or any product when the query has no hard category.

   Further rules:
   - Only products whose hard status is `violated` qualify. Eligible and unknown products never
     do.
   - A query with no hard constraint (`gq-p20`) uses ordinary catalog products as
     out-of-catalog probes.
   - A short tier is filled from the other tier. Anything still missing is reported as a
     shortfall.
   - The reason a product is a negative stays private.
4. **Blind order.** `sha256("blind-1|query_id|product_id")`, independent of sources and
   scores.
5. **Cap.** At most 60 per query. Over the cap, nothing is frozen and nothing is trimmed, and
   only aggregate counts are reported (`PoolCapExceeded`).

### Contract extensions (Session C2)

- **`card-1` product card** (`evals/contracts/cards.py`). The exact annotation projection:
  - product id, title, description, category, subcategory, brand, price, currency and the
    category attributes;
  - never seller, availability, rating or review count.

  `PoolItem` gained `card_sha256` (the card hash) next to `product_content_sha256` (the
  catalog record hash). Both are re-checked against the catalog before annotation.
- **`PoolProvenance`** (role `provenance`) is now **one canonical JSON object**, replacing
  `ProvenanceEntry` JSONL. It holds:
  - the deterministic run context: queries manifest, catalog identity, approved settings,
    model pins with config hashes, component and library versions, and the committed runtime
    tree ids;
  - every source run: endpoint, search version, ranked product ids, applied and ignored
    filters, parser and filter-policy versions, dense status, and reranker mode;
  - the per-product entries: inclusion reason plus each source's rank and score.

  `run_id` is the first 16 hex digits of the context's SHA-256. It contains no time, path or
  database name.
- **`PoolReport`** (new generated role `pool_report`, added at `pool_frozen`). Per-query
  aggregate counts only.

### Blind annotation CLI (`evals/annotation/`)

```text
uv run python -m evals.annotation status
uv run python -m evals.annotation annotate --annotator ann-1
uv run python -m evals.annotation annotate --annotator ann-1 --compact
uv run python -m evals.annotation validate
```

What it reads:
- It reads only a verified `pool_frozen` stage: public files only, never the provenance.
- It re-checks every product's content and card hash, so annotation fails if a product
  changed.

What it shows:
- one pair at a time, by query and then blind position;
- the query, its interpretations, the annotator's own gold constraints and product intents,
  and the `card-1` card.

What it never shows: source, rank, score, inclusion reason, parser output, filters, seller,
availability, rating, review count or eligibility.

How labelling works:
- The annotator types and confirms the label (`r` / `b` / `n`) and its allowed relation,
  confidence, rationale, `needs_adjudication` and `catalog_issue`. Nothing is prefilled or
  suggested.
- A rationale is required for `borderline`, low confidence, and `relevant` with an unknown hard
  attribute.
- `relevant` is refused for a product that violates a hard gold constraint.

Compact mode (`--compact`, opt-in; the default mode is unchanged):
- The whole decision is typed on one line as
  `<label><relation><confidence><adjudication><catalog_issue>!`, for example `n2hnn!`
  (not_relevant / off_target / high / no adjudication / no catalog issue). A rationale follows
  ` | ` on the same line, for example `b1mnn! | Partially matches the stated intent`.
- Codes: label `r` / `b` / `n`; relation, numbered as in the default mode's menu: after `r`, 1
  exact_match and 2 satisfies_intent; after `b`, 1 partial and 2 substitute; after `n`, 1
  complement, 2 off_target and 3 out_of_catalog; confidence `h` / `m` / `l`; adjudication `y` /
  `n`; catalog issue `y` / `n`. The codes are shown at the start of the session and on `?`.
- The trailing `!` is the explicit confirmation, so there is no separate save prompt. Every
  field must be typed: there are no defaults, suggestions, proposals or bulk entry.
- These save nothing and ask for the same pair again: a malformed entry, a relation the label
  does not allow, a missing `!`, a missing required rationale, and `relevant` for a hard
  violation.
- The rationale, hard-constraint, validation, atomic-save, lock and resume rules are those of
  the default mode. `q` stops in the same way.

Storage:
- The working file is
  `data/processed/golden_annotation/<pool manifest prefix>/primary_judgements.jsonl`
  (git-ignored). It is bound to the pool by `binding.json`.
- It is atomically replaced after every judgement, and resuming re-validates it.
- These are refused: duplicates, foreign handles, unknown pairs, records outside the time
  window, a wrong rubric, and a binding to another pool.

Binding time:
- `binding.json` records a UTC `created_at` once, when annotation work is initialized. It is
  never changed on resume.
- Every judgement must be at or after both the query confirmation time and `created_at`;
  equality is allowed. `validate`, `seal_primary check` and `seal` all enforce this.
- Naive, non-UTC or malformed timestamps are refused.
- This protects against accidental or pre-seal backdating only. It is **not** cryptographic
  tamper-proofing: the working file and binding are ordinary local files until the annotator
  seals the round, and the seal then binds the exact bytes by SHA-256. The pool, content and
  card hash checks remain mandatory.

Stopping:
- Type `q` at any prompt to stop. End of input (EOF, for example when stdin is not a terminal)
  ends the session the same way, with exit code 0 and the message "Input ended; progress
  saved. Resume by running the annotation command again."
- Either way, every confirmed judgement is kept, a partly answered pair is never saved, and the
  lock is released. Annotation needs an interactive terminal; a non-interactive `!` command
  ends at the first prompt.

Session lock:
- `annotate` creates `annotation.lock` in the work directory with exclusive creation before
  reading any judgement. It holds only the pool manifest hash, the annotator handle, the
  process id and the UTC start time.
- A second session on the same work directory refuses to start. Separate work directories do
  not block each other.
- The lock is removed on normal exit, on a handled error and on Ctrl-C (KeyboardInterrupt).
- After a hard kill the lock remains. It is never removed automatically, and there is no
  override flag. Every later `annotate` and the seal tooling refuse, with instructions to check
  that no session is running, confirm `validate` passes, and delete the lock by hand.
- `status` and `validate` are read-only and never take the lock.

### Review protocol amendment `review-2` (approved 2026-10-15; since run on real data, see "Status")

**What changed and what did not.** The original single-annotator protocol (D5, now called
`review-1`) planned a 72-hour-delayed **intra-annotator** consistency round: `ann-1` re-labels
the cs-1 sample. That round will **not** be carried out, so the original protocol is not
completed unchanged. The approved amendment `review-2` replaces it with a blind **second-human**
review:

- an independent second annotator, `ann-2`, re-labels the same cs-1 sample (ceil(20% × 568) =
  114 pairs for the real pool) blind to `ann-1`'s labels;
- **inter-annotator agreement** is reported on that sample;
- **delayed intra-annotator consistency is not measured**. No intra-annotator figure exists or
  will be reported, and the inter-annotator figures are never presented as one;
- every disagreement, and every pair `ann-2` flagged as needing adjudication or as a catalog
  issue (also when the two labels agree), is resolved by a **joint consensus record** of both
  humans.

The D5 text above and every review-1 contract, validator and test are kept unchanged as history.
Their only change is that the legacy tests now name the review-1 order explicitly; see "Legacy
test changes" below.

**Unchanged.**
- The pool, the 568 primary judgements (working-file SHA-256 `3f50829a…8953925`) and the
  committed `queries_frozen` / `pool_frozen` manifests (bytes and hashes re-verified).
- The primary seal tooling and its outputs, including the cs-1 sampling logic. `cs-1` is already
  fixed in the `pool_frozen` manifest's `versions`, so the second-review sample is exactly the
  sample `seal_primary` writes.
- The targeted adjudication queue (built at the primary seal from `ann-1`'s labels and flags)
  and single-annotator (`ann-1`) adjudication of queued items.
- review-1 behaviour: `validate_adjudication_round` and the review-1 freeze rules are unchanged.
  They still do not require every targeted-queue item to have an adjudication record. The
  stricter completeness rule below applies to review-2 only.

**Contracts** (`evals/contracts/`):
- `Round.SECOND_REVIEW`, distinct from `Round.CONSISTENCY`.
- `Stage.SECOND_REVIEW_SEALED` and an explicit manifest field `review_protocol: "review-2"`.
  - The field is set from `second_review_sealed` onwards. A missing field means review-1 and is
    never serialized, so legacy manifest bytes do not change.
  - Lifecycles: review-1 is `queries_frozen → pool_frozen → primary_sealed → labels_frozen →
    provenance_unsealed`. review-2 inserts `second_review_sealed` after `primary_sealed`.
  - Stage role sets and transitions are branched by protocol. The protocol can switch only from
    review-1 to review-2, and only on the step into `second_review_sealed`.
- New roles:
  - `second_review_judgements` (recorded), `agreement_report` (generated) and
    `joint_resolution_queue` (generated, `joint_resolution_queue.jsonl`), added at
    `second_review_sealed`;
  - `consensus_adjudications` (recorded), which replaces `consistency_judgements` at the review-2
    `labels_frozen`.
- `JointResolutionItem` (the joint-resolution queue): one item per sampled pair that needs joint
  resolution, with sorted reasons and **no label**. The reasons are:
  - `second_review_disagreement`: the two labels differ;
  - `second_review_needs_adjudication`: `ann-2` answered yes to "needs adjudication";
  - `second_review_catalog_issue`: `ann-2` answered yes to "catalog issue".

  Both flags are preserved as separate reasons, including when the labels agree.
- `ConsensusAdjudication` (a joint record) records:
  - the reasons it resolves, both participants (two distinct handles), the primary and
    second-review labels, the agreed label and relation, a required rationale and a time;
  - it exists only for a routed pair, and only once a joint resolution is reached; the label
    may stay unchanged;
  - the disagreement reason must be present exactly when the two labels differ.
- Catalog issues are noted in the joint record only. Catalog data is never edited.
- A consensus that changes the primary label needs exactly one `LabelChange` of kind
  `consensus`, made by one of the participants.
- Final labels follow `derive_final_judgements_review_2`: the joint record for a routed pair,
  else a queued single-annotator adjudication, else the primary label.

**Validators** (`evals/contracts/validation.py`):
- `validate_second_review_round`:
  - the sample must equal its cs-1 regeneration from the sealed primaries;
  - exactly the sampled pairs are judged, each once, by `ann-2` only (never the primary
    annotator);
  - every judgement is at or after the primary seal and at or before the second-review seal,
    under the primary judgement's rubric;
  - the hard-constraint rules apply;
  - no 72-hour delay applies, because that delay only guards against self-recall.
- `validate_review_2_adjudication` (the review-2 freeze gate; nothing unresolved passes):
  - the joint-resolution queue must equal its regeneration from the sealed primary and
    second-review rounds;
  - every routed pair (a disagreement or an `ann-2` flag) needs exactly one joint record naming
    both annotators, resolving exactly its routed reasons, dated at or after the second-review
    seal; no other pair may have one;
  - **a missing joint record is an unresolved item and blocks the label freeze**;
  - a joint resolution is never inferred or generated;
  - a targeted-queue pair that was also routed for joint resolution is settled by its joint
    record. A single-annotator decision is refused for any routed pair;
  - every **mandatory** targeted-queue item that is not routed must be resolved before the
    freeze by a single-annotator (`ann-1`) adjudication under the unchanged review-1 rules.
    **An unresolved mandatory item blocks the freeze.** It is resolved by `ann-1` alone, not
    jointly; that is unchanged from review-1;
  - an **optional** review candidate may be adjudicated the same way. If it is not, its sealed
    primary judgement stays the final label (`decided_in: primary`); it is never reported as
    resolved or re-reviewed.
  - The mandatory/optional split is the scope revision of 2026-10-16 below. Before it, this
    validator required **every** targeted-queue item to be resolved before the freeze.
- `validate_final_judgements_review_2` and the protocol-aware `validate_labels_frozen_at`.

**Scope revision (approved 2026-10-16).** The first review-2 text (above, as approved on
2026-10-15, and implemented in `validate_review_2_adjudication`) said: "every item in `ann-1`'s
targeted queue must be resolved before the freeze … An unresolved targeted-queue item also
blocks the freeze." That requirement did appear, and it is superseded, not withdrawn
retroactively. A read-only audit after the second-review seal showed that it was not part of
D5 or of review-1: under review-1 the targeted queue is a set of review candidates, and the
review-1 validators do not require an adjudication record for every item. Applied to the real
pool, the rule made 315 distinct pairs mandatory, 218 of them selected only automatically.
- **Mandatory** (block the freeze until resolved):
  - every joint-resolution pair, unchanged (21 on the real pool: 15 label disagreements and 6
    pairs with only `ann-2` flags);
  - every targeted-queue pair not routed for joint resolution that carries any reason other
    than `borderline` or `ambiguous_query`: `ann-1`'s `needs_adjudication` or `catalog_issue`
    flag, `low_confidence` (MASTER_PLAN §6, rule 3), or `hard_constraint_unknown` (missing
    hard-constraint evidence). 76 pairs on the real pool;
  - an item is optional only when **every** reason is `borderline` or `ambiguous_query`, so a
    mandatory reason always wins, and any reason added later is mandatory by default
    (`review_sets.split_review_2_targeted`).
- **Optional:** the 218 pairs selected only because the primary label is borderline or the query
  is ambiguous. If not adjudicated they keep their sealed primary judgements.
- **Conflicting evidence.** The strict dataset's documented conflicting- or missing-evidence
  cases are label disagreements (mandatory, joint) and `hard_constraint_unknown` (mandatory; 0
  pairs on the real pool). The "signal conflicts" in `docs/weak-label-development-m9.md` (42)
  are machine-only weak-label signals from a separate track. They are not used here, because
  making them freeze blockers would bring machine output into the blind human workflow and
  turn model output into a hard requirement. The mandatory count is therefore 97 distinct pairs.
- **Unchanged:** every sealed judgement, manifest, queue and the agreement report (byte for
  byte); the blind second review; the joint-resolution rules; the review-1 contracts.

**Agreement report `iaa-1`** (`evals/metrics/agreement.py`):
- It is generated once, from the sealed bytes, when the second review is sealed and before any
  consensus.
- Contents:
  - the 3×3 confusion matrix (rows: primary label; columns: second-review label);
  - observed agreement, chance agreement and unweighted Cohen's kappa for the three labels, and
    for the strict and lenient binary collapses;
  - observed agreement per stratum (one stratum per primary label).
- Arithmetic is exact. Values are 10-decimal strings rounded half-even. Kappa is null when chance
  agreement is 1.
- Relation-facet agreement is omitted by decision.
- The report carries `statistic: inter_annotator_agreement`,
  `intra_annotator_consistency: not_measured` and a fixed caveat. Caveat: cs-1 is stratified by
  `ann-1`'s labels (round-robin), so it over-represents rarer labels, and the figures describe
  the sample and its strata only. **No population or weighted estimate is made.**
- **Agreement is not proof of accuracy.** It measures how often two reviewers chose the same
  label under the same rubric. Both can agree on a wrong label, and shared rubric gaps (see the
  rubric documents) can raise agreement without making labels more correct.

**Blind reviewer bundle** (`evals/annotation/reviewer_bundle.py`,
`evals.runners.build_reviewer_bundle`):
- It is built from the verified `primary_sealed` stage **without opening**
  `primary_judgements.jsonl` or `adjudication_queue.jsonl`. A test deletes both files and the
  bundle still builds.
- It is written to a new directory **outside the repository**. It holds exactly four files:
  - `bundle.json`: the sample pairs in cs-1 blind order, each with the query text and
    interpretations, the frozen gold constraints and soft intents, the rendered `card-1` card and
    its hash, and the two hard-constraint flags. The primary tool also used those flags only to
    refuse `relevant` and to require a rationale.
  - the rubric file;
  - `review.py`, a byte-identical copy of `evals/annotation/reviewer_tool.py` that needs only the
    Python standard library;
  - `README.txt`. It tells `ann-2` to review independently: no primary labels, no machine or AI
    labels or proposals, and no project AI-assistant conversations.
- It excludes:
  - primary labels, rationales and confidences;
  - sample allocation counts;
  - machine proposals and weak labels;
  - provenance, sources, ranks and scores;
  - agreement figures and adjudication queues;
  - the repository and its history.
- `review.py` asks step by step by default, in the order: label, an allowed relation,
  confidence, rationale (required under the existing rules), needs adjudication, catalog issue.
  It then shows a summary of all six answers and saves only on an explicit `y`; anything else
  discards that pair's answers. An invalid answer is explained and asked again.
  `--compact` keeps the primary compact mode: the same codes and the trailing `!` confirmation.
  Both modes apply the same rationale, hard-constraint and free-text rules, an exclusive lock,
  atomic saves and resume, and write identical canonical `Judgement` JSONL (round
  `second_review`, `ann-2`).
- Changing `review.py` changes `tool_sha256` and therefore the bundle's SHA-256. A bundle built
  with an earlier tool is never edited in place: it is rebuilt into a new directory. The
  sampled pairs and their order come from the sealed cs-1 sample and do not change. An old
  `binding.json` is refused by the new bundle, so the new workspace binds itself on its first
  `annotate`. `seal_second_review check` accepts only a workspace whose `bundle.json` and
  `review.py` match a regeneration from the current repository.
- **Blindness is procedural, not cryptographic isolation.** The bundle simply omits these items.
  `ann-2` must not look for them elsewhere before sealing. After the primary seal they are in the
  repository.
- The rubric is supplied explicitly (`--rubric`) because the repository has no standalone
  `rubric-1` text. When this was written no real bundle had been generated; the real second
  review was later carried out and sealed (`second_review_sealed`).
  - `docs/rubric-1-reviewer-transcription.md` is the maintainer record. It was approved as a
    record of the existing rules, including their gaps and conflicts, and is kept unchanged.
  - `docs/rubric-1-reviewer-copy.md` is the approved reviewer copy given to `ann-2`. It has no
    draft header and no maintainer section, and keeps every "not specified" statement.
- Approved reviewer-presentation exclusions (the reviewer copy only; the query records, recorded
  constraints and general rubric are unchanged):
  - query `notes` that the primary CLI never showed (gq-p04, gq-p10, gq-p12, gq-p16, gq-p17,

  - **gq-p20:** the query-specific wording "An out-of-catalog category intent … no product is
    hard-eligible". It states a catalog-wide conclusion that the primary CLI never showed;
  - hard-eligible counts and product IDs, which are catalog facts that could act as hints.

### Retrieval-metric evaluator (`evals/metrics/retrieval.py`, `eval-1`)

**Definitions.**

| Metric | Definition |
|---|---|
| Precision@K | relevant in the top K / K (fixed denominator) |
| Recall@K | pooled: relevant in the top K / relevant judged pairs |
| MRR@K | reciprocal rank of the first relevant result, 0 if none |
| NDCG@K | gains 2 / 1 / 0; IDCG from the query's judged labels |
| CSR@K | `hard` and `fp1` separately: satisfied / returned, with unknown reported separately; plus an all-satisfied flag |
| Irrelevant-result rate@K | (`not_relevant` + unjudged) / returned |
| Zero-result | 1 when nothing was returned |
| Correct-empty | for zero-relevant queries only |

**Conventions.**
- K is 5, 10 and 20; the primary K is 10.
- Strict relevance (primary) and lenient relevance (secondary) are both always reported. There
  is no blended score.
- Unjudged results count as not relevant and are counted (`unjudged@K`).

**Zero-relevant queries.** Recall and MRR are null per definition for zero-relevant queries.
NDCG is null when the query has no relevant or borderline judged pair. Null values are never
averaged as 0.

**Aggregation.** Macro means over the defined queries, each with `n` and `excluded`.

**Serialization.** Values are 10-decimal strings, rounded half-even, inside a versioned config
block.

**Status.** It is tested only on hand-calculated synthetic fixtures (`test_golden_metrics.py`).
No strict human-reviewed metric result exists. Milestone 10 runs the official V0–V3 comparison
after the labels freeze.

### Stale freeze staging

A `.freeze-staging-*` directory left behind by a hard kill is now handled as follows:

- every runner and the annotation store detect it at startup;
- it is refused with cleanup instructions;
- it is never deleted automatically, and never read as frozen output.

### Session C2 limitations

- **Pooled-recall bias.** For `gq-p01`, `gq-p11`, `gq-p13` and `gq-p15`, more than 25 products
  are eligible, so completion does not run and pooled recall is biased (`docs/spec.md` §9.2).
  The negatives act as a pool-miss probe.
- **Shared lists across sources.** For queries where lexical returns nothing, dense, V1, V2 and
  V3 return largely the same 20 products. Pools are therefore well below the 60 cap.
- **Scores as `repr(float)`.** Byte identity held across three runs on this machine, with the
  same libraries and CPU. It is not claimed across other hardware or library versions; the run
  context records the library versions for that reason.
- **Private provenance location.** It exists only in this working copy's ignored
  `data/processed/`, and it must be preserved until `provenance_unsealed`.
- **No integration test.** No integration test file was added. The real retrieval path was
  exercised by the actual runs above, and all unit tests use synthetic fakes.
